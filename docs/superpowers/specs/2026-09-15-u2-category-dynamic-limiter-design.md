# U2 分类动态单种限速

## 目标

新增独立 `u2-limiter` 服务，管理现有九个 qBittorrent 节点中分类严格为
`U2` 的种子。服务对每个种子设置真实的 qB 单种上传/下载限速，使 tracker
announce 区间的上传平均速率保守地低于 50 MiB/s。

## 前提与数据来源

qBittorrent 5.1.4 的 `/api/v2/torrents/trackers` 响应不提供可用的
`next_announce`，但 `/api/v2/torrents/properties` 的 `reannounce` 字段实际提供
距离下次汇报的秒数。已在生产节点验证该字段为正倒计时。

动态模式只使用 qB 的 `reannounce` 与 `total_uploaded`。限速器通过倒计时从接近
零跳回完整周期来确认一次 announce，并以该瞬间的 `total_uploaded` 建立新周期
基线。首次观测或尚未确认一次倒计时回跳时，不推测周期，使用保守限速。

## 明确不做

- 不访问 U2 网站，不使用、保存或读取 U2 Cookie、UID 或 passkey。
- 不执行放魔法，不调用 U2 的 promotion 接口，不请求任何 U2 URL。
- 不修改 Java `u2magic` 容器、其 `runtime/data` 或现有上传选择逻辑。
- 不修改 qB 全局限速，不修改非 `U2` 分类的种子。
- 不启用 `tc`、SSH 或任何网卡级限速。

## 服务和配置

新增一个单独构建的 Python 服务及持久化卷。配置文件只包含九个 qB WebUI 节点与
限速参数；qB 凭据不写进 Git。运行时从挂载的私有配置读取，服务器上的文件权限
为 `0600`。

每轮轮询：

1. 查询每个 qB 的 `U2` 分类种子及 tracker 状态。
2. 忽略 tracker 不属于配置允许 U2 tracker 主机名集合的种子。
3. 查询每个入选种子的 qB properties，读取 `reannounce` 与 `total_uploaded`。
4. 持久化每个 `节点 + torrent hash` 的上传基线、观测时间、倒计时、已确认的
   announce 周期长度和当前由本服务施加的限速。
5. 根据该 announce 区间已上传量和剩余时间，计算安全的单种上传上限；只改变
   本服务管理的种子。

首次观测、状态丢失、properties 请求失败或 tracker 信息不足时，使用 45 MiB/s 的
保守单种上限。倒计时回跳确认后，限速器以该周期的上传预算除以剩余时间计算上限：
前段可以高于 50 MiB/s，后段自动收紧，以使整个 announce 区间的平均值保守地低于
50 MiB/s。计算必须保留配置化安全余量；若剩余预算已耗尽则设为极低的保护值而不是
解除限速。若原始限速为有限值且不低于计算上限，则保留原始限速；原始限速为无限时
仍写入计算上限，不能因未知的后续突发而提前解除限速。限速值统一按 qB API 的
字节/秒传递，配置使用 MiB/s。

## 安全与故障策略

- qB 请求失败：记录节点错误，不向其他节点扩散操作；保留已设置的限速。
- properties 请求失败或 `reannounce` 无效：保持 45 MiB/s 的保守上限，不因
  不确定性放开。
- 服务停止：不批量解除限速，避免停机期间新出现的超速；恢复后从持久化状态
  继续。提供显式 `--release-managed-limits` 管理命令用于人工退出。
- 只对服务自己标记/持久化为已管理的种子解除限速，避免覆盖用户的手动限速。
- 所有日志禁止输出 qB 密码、完整 tracker query。

## 验证

测试覆盖：

1. 非 `U2` 分类绝不调用 qB 限速 API。
2. 首次观测和 tracker 数据缺失时施加 45 MiB/s。
3. `reannounce` 无效、properties 请求失败或尚未出现倒计时回跳时保持 45 MiB/s。
4. 倒计时回跳建立的基线和周期长度可跨进程重启恢复。
5. announce 周期前段可计算出高于 50 MiB/s 的限速；累计上传接近预算时自动降低，
   且整个周期的预算公式保留安全余量。
6. announce 后风险解除时只解除服务自身设置的限速。
7. 一个节点或站点观测失败不影响其它节点。
8. 持久化状态在重启后恢复。

部署前先以只读诊断模式列出九个节点实际的 U2 tracker 主机名、`reannounce` 倒计时
和可用 properties 数量；只有确认结果后才启用写入 qB 限速的运行模式。
